# 문서 리뷰 작업 지침

이 저장소에서 문서를 검토하거나 작성·수정할 때 적용한다. 주 독자는 문서 작성 또는 리뷰를 맡은 개발자와 코딩 에이전트다. 목표는 원문의 사실과 기술적 의미를 보존하면서, 독자가 필요한 정보를 정확하고 쉽게 얻도록 만드는 것이다.

## 1. 시작 전 확인

1. 이 파일이 있는 저장소의 루트를 기준으로 모든 상대 경로를 해석한다.
2. 사용자의 작업 범위를 확인한다. 범위에는 대상 문서, 작업 목적, 문서 유형, 그리고 원문 수정 허용 여부가 포함된다.
3. 문서 유형이 지정되지 않았으면 독자의 읽기 방식을 먼저 판단한다. 판단 근거가 부족하면 문서를 임의로 수정하지 말고 `확인 필요`로 보고한다.
4. 작업 유형을 구분한다.
   - **리뷰**: 문제와 수정 제안만 제시한다. 원문은 바꾸지 않는다.
   - **수정**: 체크리스트에 맞게 원문을 고친다.
   - **리뷰 리포트 저장**: 리뷰 결과를 별도 Markdown 파일로 저장한다.

## 2. 체크리스트 선택과 읽기

모든 작업에서 다음 공통 체크리스트를 순서대로 읽고 적용한다.

1. `02_checklists/00_common/01_common_quality.md`
2. `02_checklists/00_common/02_reader_and_topic.md`
3. `02_checklists/00_common/03_outline.md`

그다음 독자의 읽기 방식을 선택한다.

- **사전형**: 특정 정보를 찾아 읽는 문서다. 매뉴얼, 절차서, 기능 명세서, 프로젝트 README가 해당한다.
- **읽기형**: 처음부터 끝까지 읽으며 논리를 따라가는 문서다. 개발 보고서, 제안서, 기술 블로그가 해당한다.
- 유형을 판단할 수 없으면 추정하지 말고 `확인 필요`로 보고한다.

## 3. 리뷰와 수정 절차

1. 문서의 독자, 독자 목표, 범위, 문서 유형을 확인한다.
2. 적용할 체크리스트의 각 항목을 원문과 대조한다.
3. 발견 사항에는 문서 위치, 체크리스트 근거, 문제, 수정 방향을 함께 기록한다.
4. 수정 작업이면 사실을 바꾸지 않는 범위에서 원문을 고친다. 구조 변경은 제목과 참조 관계에도 영향을 주는지 확인한다.
5. 수정 뒤 제목과 소제목만 다시 읽어 정보 위치와 논리 흐름을 검증한다.

다음 원칙을 지킨다.

- 사실, 수치, 정책, 기술 동작, 의도는 근거 없이 추가·삭제·변경하지 않는다.
- 근거가 부족하거나 여러 해석이 가능한 내용은 그럴듯하게 보완하지 말고 `확인 필요`로 분리한다.
- 체크리스트가 충돌하거나 적용 여부가 불명확하면, 임의로 결정하지 말고 판단 근거와 함께 `확인 필요`로 보고한다.
- 리뷰 작업에서는 원문을 변경하지 않는다. 수정은 사용자가 명시적으로 요청했거나 허용한 경우에만 한다.
- 다른 문서나 시스템에 영향을 주는 사실 확인, 정책 변경, 되돌리기 어려운 작업은 수행 전에 사용자 확인을 받는다.

## 4. 산출물과 완료 기준

작업을 마치면 결과를 먼저 짧게 알리고 다음 내용을 포함한다.

- 문서 유형과 적용한 체크리스트 파일
- 핵심 발견 사항 또는 반영한 변경 사항
- `확인 필요` 항목과 그 이유. 없으면 없다고 적는다.
- 원문 수정 여부와 수정한 파일

사용자가 리뷰 결과를 Markdown 파일로 저장해 달라고 요청하면, 먼저 `03_docs_template/01_agent/document-review-report-template.md`를 읽고 해당 형식을 따른다. 템플릿의 안내 문구와 예시 행은 실제 결과로 바꾸거나 제거한다. 구조 변경이 필요하지 않으면 `제안 구조`는 생략한다.

다음 조건을 모두 충족하면 작업을 완료한다.

1. 선택한 모든 체크리스트를 적용했다.
2. 리뷰와 수정의 범위를 구분해 지켰다.
3. 제목과 소제목의 흐름을 마지막으로 검토했다.
4. 확인이 필요한 사실이나 판단을 숨기지 않고 보고했다.
