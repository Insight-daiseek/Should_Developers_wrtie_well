# 장문 문서 검토를 위한 A2A 설계안

이 문서는 문서 작성·수정 체크리스트를 여러 코딩 에이전트가 순차적으로 적용하는 A2A(Agent-to-Agent) 검토 구조를 정의한다. 목적은 장문 문서에서 검토 관점을 분리하고, 변경 근거와 사실 확인 필요 항목을 추적하는 것이다.

## 1. 적용 기준

짧은 문서는 단일 에이전트가 모든 체크리스트를 적용하는 편이 빠르고 문맥을 유지하기 쉽다. A2A는 다음 상황에서 사용한다.

- 문서가 길어 한 에이전트가 전체 구조와 세부 문장을 안정적으로 검토하기 어려운 경우
- 여러 독자 또는 여러 문서 유형을 함께 고려해야 하는 경우
- 구조 변경의 영향이 크거나 변경 근거를 남겨야 하는 경우
- 문서 수정과 사실·정책·기술 검토를 분리해야 하는 경우

| 문서 전체 분량 | 권장 방식 |
| --- | --- |
| 1~15쪽 | 단일 에이전트 |
| 15~40쪽 | 단일 에이전트와 독립 검토 1회 |
| 40~100쪽 | A2A 파이프라인 |
| 100쪽 이상 | 장별 코디네이터를 둔 계층형 A2A |

페이지 수는 편집 형식에 따라 달라지므로 참고 기준으로만 사용한다. 더 중요한 기준은 개별 에이전트가 검토하는 섹션의 범위다.

- 섹션 편집 에이전트의 담당 범위: 약 5~10쪽
- 전체 코디네이터가 원문 전체를 직접 읽는 범위: 약 50쪽 이하
- 50쪽을 넘는 문서는 원문 전체 대신 문서 지도, 장별 요약, 용어집, 변경 이력을 전달한다.

## 2. 전체 흐름

```text
원문
  ↓
[1] 코디네이터: 문서 지도·작업 범위 생성
  ↓
[2] 독자·주제 분석가 (02)
  ↓
[3] 아웃라인 분석가 (03)
  ↓
구조 변경 승인 게이트
  ↓
[4] 섹션 편집 에이전트들: 장·절 단위 병렬 작업
  ↓
[5] 유형별 검토자 (04 또는 05)
  ↓
[6] 공통 품질 검토자 (01)
  ↓
[7] 오케스트레이터: 충돌 해소·최종 통합
  ↓
최종 문서 + 변경 내역 + 확인 필요 목록
```

구조 검토가 끝나기 전에는 섹션 편집을 시작하지 않는다. 여러 에이전트가 같은 원문을 동시에 직접 수정하지 않도록 한다.

## 3. 역할과 책임

| 단계 | 역할 | 참조 체크리스트 | 산출물 | 직접 수정 |
| --- | --- | --- | --- | --- |
| 1 | 코디네이터 | 전체 | 문서 지도, 용어집, 작업 범위 | 아니오 |
| 2 | 독자·주제 분석가 | `02_checklists/00_common/02_reader_and_topic.md` | 독자·목적·범위 문제 | 아니오 |
| 3 | 아웃라인 분석가 | `02_checklists/00_common/03_outline.md` | 순서·제목·계층 구조 문제 | 아니오 |
| 4 | 섹션 편집자 | 공통 01~03, 유형별 기본, 세부 유형 | 담당 장의 수정안 | 담당 범위만 |
| 5 | 유형별 검토자 | `02_checklists/10_reference_documents/10_reference_base.md` 또는 `02_checklists/20_reading_documents/20_reading_base.md`와 세부 유형 파일 | 탐색성 또는 논리 흐름 문제 | 아니오 |
| 6 | 공통 품질 검토자 | `02_checklists/00_common/01_common_quality.md` | 명확성·중복·핵심 문장 문제 | 아니오 |
| 7 | 오케스트레이터 | 전체 | 충돌 해소와 최종 통합 | 최종 통합만 |

유형별 검토자는 문서의 읽기 방식에 따라 하나만 선택한다.

- 매뉴얼, 명세서, 절차서처럼 특정 정보를 찾아 읽는 문서: 04 사전형 문서 체크리스트
- 보고서, 기술 블로그, 제안서처럼 처음부터 읽으며 논리를 따라가는 문서: 05 읽기형 문서 체크리스트

## 4. 문서 분할 규칙

문서를 글자 수 기준으로 임의 분할하지 않는다. 확정된 아웃라인을 기준으로 장·절 단위로 나눈다.

- 각 섹션은 하나의 주제와 하나의 독자 목적을 가져야 한다.
- 앞뒤 섹션에 의존하는 정의, 용어, 전제는 문서 지도에 기록한다.
- 공통 도입부, 용어집, 결론, 목차는 섹션 편집자가 직접 수정하지 않는다.
- 담당 섹션의 수정이 다른 섹션에 영향을 주면, 직접 수정하지 않고 `cross_section_issue`로 보고한다.
- 모든 섹션 편집이 끝난 뒤에만 오케스트레이터가 전체 문서를 통합한다.

100쪽을 넘는 문서는 장별 코디네이터를 둔다.

```text
전체 코디네이터
  ├─ 장 A 코디네이터
  │  ├─ 섹션 A-1 편집자
  │  └─ 섹션 A-2 편집자
  ├─ 장 B 코디네이터
  └─ 장 C 코디네이터
```

전체 코디네이터는 장별 결과와 문서 지도만 취합한다. 장별 코디네이터가 장 안의 섹션 간 용어·참조·흐름을 검토한다.

## 5. A2A 전달 형식

에이전트는 자연어 요약만 전달하지 않는다. 모든 발견 사항은 위치, 근거, 체크리스트 항목, 권고안을 포함한 구조화된 형식으로 전달한다.

```yaml
document_profile:
  document_type: reference
  primary_reader: "신입 백엔드 개발자"
  reader_goal: "API 오류 대응 방법 확인"
  immutable_facts:
    - "API 이름과 상태 코드는 변경 금지"

finding:
  id: OUTLINE-003
  checklist: 02_checklists/00_common/03_outline.md
  severity: high
  location: "## 오류 처리"
  evidence: "인증 오류가 재시도 절차 뒤에 위치함"
  recommendation: "인증 오류를 재시도 절차 앞에 배치"
  requires_confirmation: false

patch_proposal:
  target: "docs/api-guide.md"
  scope: "## 오류 처리"
  change_type: restructure
  depends_on:
    - OUTLINE-003
```

필수 필드의 의미는 다음과 같다.

- `id`: 결과를 추적하고 중복을 제거하는 식별자
- `checklist`: 판단의 근거가 된 체크리스트 파일
- `location`: 제목 또는 고유한 문서 위치
- `evidence`: 원문에서 확인한 근거
- `recommendation`: 사실을 추가하지 않는 수정 방향
- `requires_confirmation`: 사용자 또는 문서 소유자의 확인이 필요한지 여부

## 6. 결정 게이트와 충돌 해소

### 구조 변경 승인 게이트

02와 03의 검토가 끝나면 오케스트레이터는 구조 변경안을 확정한다. 다음 단계의 섹션 편집자는 확정된 구조 안에서만 작업한다.

### 사실 확인 게이트

수치, 정책, 기술 동작, 의사결정 근거가 불명확하면 수정하지 않는다. 해당 내용은 `확인 필요` 목록으로 분리한다.

### 충돌 해소 우선순위

오케스트레이터는 다음 우선순위로 충돌을 해결한다.

```text
사실·정책 보존
→ 사용자의 명시적 요청
→ 독자와 문서 목적
→ 문서 유형별 체크리스트
→ 아웃라인과 정보 흐름
→ 문장·스타일 개선
```

예를 들어 문장을 짧게 만드는 수정이 명세의 조건·예외를 누락시킨다면, 사실과 기술적 의미 보존을 우선한다.

## 7. 최종 산출물

오케스트레이터는 다음을 제출한다.

1. 최종 통합 문서 또는 적용 가능한 수정안
2. 반영한 발견 사항 목록과 변경 이유
3. 반영하지 않은 발견 사항과 그 이유
4. `확인 필요` 항목 목록
5. 적용한 체크리스트와 문서 유형

최종 통합 뒤에는 제목과 소제목만 읽어 정보 위치와 논리 흐름을 한 번 더 검증한다.
